# Design — CLI-утилита `smoke`: команда `smoke --version`

Документ закрывает архитектурные вопросы, оставленные узлом `requirements`, и
фиксирует механику, которую требования и behaviour-spec сознательно оставили
неопределённой: точки врезки, формы инвокаций, формы коммитов и эвиденции, а
также рамки red-теста. Продуктовые решения (объём `OUT-01`, формат вывода
`NFR-02`, обязательность `FR-04`) здесь не переоткрываются — они входные.

Вышестоящих узлов ровно два: `10-requirements.md` (идентификаторы `FR-01`…
`FR-04`, `NFR-01`…`NFR-03`) и `15-behaviour-spec.md` (сценарии `BEH-01`…
`BEH-09`). Идентификаторы используются дословно.

## Резолюции открытых вопросов

Входной набор — архитектурные вопросы узла `requirements`: `Q-01`, `Q-02`,
`Q-03`. Вопрос `Q-04` принадлежит роли `product` и на этой стадии не
решается. Вопросы `Q-05` и `Q-06`, заведённые стадией behaviour-spec, по
смыслу являются механикой проверки и разобраны в разделе «Механика».

#### Q-01 · owner_role: architects · resolution: resolved

Запуск `smoke` без аргументов печатает usage на stderr и завершается с кодом
возврата `2`; на stdout не печатается ничего. Требование `FR-03` уже назвало
предлагаемым по умолчанию «стандартное поведение argparse: usage на stderr», а
`OUT-01` запрещает наделять бесфлаговый запуск собственным смыслом — значит
выбор сводился к коду возврата. Код `2` выбран потому, что `argparse` сам
отдаёт `2` на любой разбор, который он считает ошибкой использования
(неизвестный флаг, неверное значение), и отдельный код `0` для «пользователь
не передал флаг» создал бы в одной команде две несовместимые трактовки
бесполезного вызова: успех на пустом stdout и ошибку на неизвестном флаге.
Ровно одна трактовка — «вызов без `--version` есть ошибка использования» —
даёт модель кодов возврата, которую `BEH-01`/`BEH-06` проверяют без оговорок:
`0` только там, где на stdout напечатана версия. Поскольку поведение
`argparse` по умолчанию при отсутствии обязательных аргументов здесь не
срабатывает (у команды нет обязательных позиционных аргументов), usage и код
`2` на пустом `argv` выдаются явно — это механика, а не продуктовое решение;
см. «Механика». После этой резолюции acceptance `BEH-06` дополняется
ожидаемым кодом `2`, и red-тест обязан его утверждать.

#### Q-02 · owner_role: architects · resolution: resolved

`PackageNotFoundError` перехватывается на границе `main()`: на stderr
печатается одна читаемая строка о том, что дистрибутив `smoke` не установлен в
текущем окружении и что окружение создаётся через `uv sync`, на stdout не
печатается ничего, код возврата — `1`. Требование `FR-04` обязательно при
любом ответе, и `FR-01` уже отправило всю диагностику на stderr, поэтому
решение не меняет наблюдаемый контракт успешного пути — оно выбирает форму
отказа. Перехват предпочтён процессной митигации `RK-01`, потому что
митигация действует только внутри нашего же CI: сценарий `A-01` называет
запуск без установки ошибкой использования, а ошибку использования совершает
человек, которому `P-01` переслал команду, и traceback в этот момент не
говорит ему, что делать. Цена решения — один `except` и одна ветка; «сверх
одного модуля и одного теста» она не выходит, так как `BEH-07` уже
зафиксировал для этой ветки отдельный файл проверок
(`tests/test_cli_missing_distribution.py`), то есть объём ветки оплачен
behaviour-spec, а не этой резолюцией. Текст сообщения red-тестом дословно не
утверждается — см. «Рамки red-дизайна».

#### Q-03 · owner_role: architects · resolution: resolved

Проверки разводятся по трём адресам ровно так, как их уже назвал `checked_by`
behaviour-spec: `tests/test_cli.py` — `BEH-01`…`BEH-06` и `BEH-08`;
`tests/test_cli_missing_distribution.py` — `BEH-07`; `tests/manual/version-bump-checklist.md`
— `BEH-09`. Design подтверждает эту нарезку, а не перекраивает её: `target` в
`checked_by` уже утверждён вместе с behaviour-spec, и смена адресов обнулила
бы запланированные QA-проверки без выигрыша в покрытии. Внутри
`tests/test_cli.py` сценарии остаются отдельными тест-функциями с именами из
`checked_by`, а не сливаются в один тест: `BEH-05` существует отдельно от
`BEH-04` именно для того, чтобы регрессия «оформление только в TTY» падала
адресно, и слияние убило бы этот сигнал. `BEH-09` на первой поставке не
автоматизируется: его автоматизация требует теста, который мутирует
отслеживаемый `pyproject.toml` и повторно запускает менеджер пакетов, то есть
делает исход прогона зависимым от внешнего состояния, тогда как содержательная
часть `NFR-03` — «версия берётся из метаданных, а не из литерала» — уже
покрыта `BEH-02` на каждом прогоне. Итог: два автоматических файла и один
ручной чеклист; оценка `CON-03` «один модуль и один тест» остаётся
ориентиром по объёму продуктового кода, а не ограничением на число файлов
проверок.

## Механика

### Точки врезки

| Адрес | Роль |
|-------|------|
| `pyproject.toml` → `[project].version` | единственный источник значения версии (CON-01) |
| `pyproject.toml` → `[project.scripts]` | `smoke = "smoke.cli:main"` — врезка entry point (FR-02) |
| `src/smoke/cli.py` → `main(argv=None) -> int` | единственная точка входа команды; возвращает код возврата, не вызывает `sys.exit` внутри логики |
| `src/smoke/cli.py` → разбор аргументов | `argparse.ArgumentParser(prog="smoke")`, флаг `--version` как `action="store_true"` |
| `src/smoke/cli.py` → получение версии | `importlib.metadata.version("smoke")`, вызывается внутри `main()` на ветке `--version` |
| `src/smoke/__init__.py` | пакетный маркер; значения версии не содержит |

Три врезки зафиксированы потому, что от них напрямую зависит достижимость
требований, а не стиль кода:

1. **`--version` не реализуется через `action="version"`.** Встроенное
   действие принимает уже вычисленную строку в момент конструирования
   парсера, то есть `importlib.metadata.version("smoke")` вызвался бы до
   входа в обработку ошибок и на окружении из `BEH-07` дал бы traceback с
   кодом, который мы не контролируем. При `action="store_true"` обращение к
   метаданным происходит внутри `main()`, где его накрывает резолюция `Q-02`.
2. **Версия читается в рантайме вызова, а не на импорте модуля.** Импорт
   `smoke.cli` не должен падать и не должен обращаться к метаданным: иначе
   отказ по `FR-04` наблюдался бы как ошибка импорта, а не как контракт
   «пустой stdout + ненулевой код».
3. **В реализации нет ни одного обращения к `sys.stdout.isatty()` и ни одной
   ветки по каналу вывода.** `NFR-02`/`BEH-05` требуют побайтового совпадения
   вывода в терминале и в пайпе; отсутствие ветки — это способ сделать
   свойство структурным, а не проверяемым на удачу.

Модель кодов возврата, единая для всех сценариев:

| Код | Условие | Сценарии |
|-----|---------|----------|
| `0` | на stdout напечатана строка `smoke <версия>` | BEH-01…BEH-05, BEH-08, BEH-09 |
| `1` | метаданные дистрибутива недоступны (`PackageNotFoundError`) | BEH-07 |
| `2` | вызов без `--version` или с нераспознанным аргументом | BEH-06 |

### Формы инвокаций

**Человеческая инвокация** (документируется в README, процессная митигация `RK-01`):
`uv sync`, затем `uv run smoke --version`. Любая инструкция, которая
предлагает запуск из исходников без установки, считается ошибочной.

**Инвокация в проверках.** Проверки запускают не `uv run`, а консольный
скрипт, разрешённый по имени в активном окружении прогона (`shutil.which`),
из `cwd`, лежащего вне репозитория (`tmp_path`). Это прямое требование
`BEH-03`: имя команды должно разрешаться без пути к модулю и без рабочего
каталога репозитория, а вложенный `uv run` внутри теста скрыл бы проверяемое
свойство за работой менеджера пакетов. Вывод читается в байтах
(`text=False`), потому что `BEH-04`/`BEH-05` утверждают свойства байтового
буфера, а не нормализованной строки.

**Эталон версии в проверках** вычисляется в момент прогона тем же
`importlib.metadata.version("smoke")` в окружении прогона. Литерал версии и
разбор `pyproject.toml` как источник ожидаемого значения запрещены
(`RK-02`, `CON-01`).

**TTY-канал для `BEH-05`** получается через `pty.openpty()` из стандартной
библиотеки: один и тот же бинарник вызывается дважды — со stdout на
слейв-дескрипторе pty и со stdout в пайп, буферы сравниваются побайтово.
`pty` используется только в тестовой оснастке, рантайм-зависимости пакета
это не затрагивает (`CON-02`).

**Изоляция сети для `BEH-08` (резолюция `Q-05`, owner_role: architects).**
Сетевое пространство имён и внешние обёртки не используются: они требуют
привилегий и делают прогон непортируемым. Механика — подмена сокетов в
дочернем процессе: процесс команды запускается с `PYTHONPATH`,
указывающим на каталог оснастки с `sitecustomize.py`, который заменяет
конструктор сокета на падающую заглушку. Любое сетевое обращение внутри
вызова становится отказом, а требуемое поведение остаётся прежним: команда
обязана напечатать версию и выйти с `0`. Факт «0 сетевых вызовов»
проверяется живым прогоном под заглушкой, а не инспекцией `/proc` или
разбором вывода сетевых утилит.

**Окружение без дистрибутива для `BEH-07` (резолюция `Q-06`, owner_role:
architects).** `uv run` устанавливает проект, поэтому окружение берётся
изолированным: интерпретатор поднимается через `uv run --no-project
--isolated python`, код команды становится импортируемым добавлением
`src/` в `PYTHONPATH`, запуск — через вход `main(["--version"])`, `cwd` —
временный каталог. Метаданные дистрибутива в таком окружении отсутствуют по
построению, подмена `importlib.metadata` не нужна. Behaviour-spec прямо
допускает эту форму: `BEH-07` говорит «код команды выполняется в этом
окружении», а не «установленная команда».

### Формы коммитов и эвиденции

Порядок коммитов — TDD, две фазы на сценарий или на связную группу
сценариев:

1. **red** — коммит содержит только проверки и тестовую оснастку; прогон
   обязан падать, и падение обязано быть содержательным (несовпадение
   stdout, кода возврата, времени), а не `ImportError`/`FileNotFoundError`
   на отсутствующем продуктовом коде. Для первого red-коммита это значит,
   что `pyproject.toml` с `[project.scripts]` и пустой пакет создаются в
   этом же коммите: иначе red падает на отсутствии команды и ничего о
   поведении не доказывает.
2. **green** — минимальная реализация, доводящая красные проверки до
   зелёных, без кода под сценарии, которые ещё не покрыты проверками.

Эвиденция к каждой фазе — вывод реального прогона, а не пересказ:
полная команда запуска, байтовые stdout/stderr и код возврата проверяемого
процесса, замеренное wall-clock время для `BEH-08`, значение
`importlib.metadata.version("smoke")`, вычисленное в том же окружении,
версии `python` и `uv`. Для `BEH-09` эвиденция — заполненный
`tests/manual/version-bump-checklist.md`: вывод до bump, diff
`pyproject.toml`, вывод после `uv sync`, и подтверждение, что других
изменённых файлов нет.

Отдельный review-гейт, не являющийся тестом: перед green-коммитом
проверяется, что значение версии не встречается ни в одном файле, кроме
`pyproject.toml` (`CON-01`, `RK-02`). Это статическая проверка содержимого
файлов, поэтому она остаётся ручным пунктом ревью и в red-тесты не
переносится — см. «Рамки red-дизайна».

## Рамки red-дизайна

Поставка относится к классу «граница + измерение»: проверяется контракт
внешнего процесса (`argv` → stdout/stderr/код возврата) и измеримые свойства
вызова (время, отсутствие записи на диск, отсутствие сети). Отсюда рамки.

**Red-тест ОБЯЗАН проверять живьём:**

- запуск реального установленного консольного скрипта как отдельного
  процесса из каталога вне репозитория — разрешение имени команды есть часть
  утверждения (`BEH-01`, `BEH-03`);
- stdout как байтовый буфер: ровно одна непустая строка, финальный `\n`, нет
  ANSI-последовательностей и управляющих символов, нет пустых строк до и
  после (`BEH-04`);
- равенство второй части строки значению
  `importlib.metadata.version("smoke")`, вычисленному в момент прогона
  (`BEH-02`);
- побайтовое равенство двух буферов — pty и пайп — и повторяемость между
  прогонами (`BEH-05`);
- код возврата `0` на успешном пути; код возврата `2` и usage на stderr при
  пустом `argv` (`BEH-06`, после резолюции `Q-01`); ненулевой код и пустой от
  версии stdout на окружении без дистрибутива (`BEH-07`);
- wall-clock времени процесса против порога 1 с из `NFR-01` (`BEH-08`);
- неизменность файловой системы: снимок рабочего каталога и временного
  `HOME` до и после вызова, вызов выполняется с подменённым `HOME`
  (`BEH-08`);
- отсутствие сетевых обращений — живым прогоном под заглушкой сокета
  (`BEH-08`).

**Red-тест НЕ ДОЛЖЕН утверждать:**

- существование файлов и каталогов (`src/smoke/cli.py`, `pyproject.toml`,
  `tests/`) — наличие файла не есть поведение;
- содержимое `pyproject.toml`: ни наличие секции `[project.scripts]`, ни
  строку entry point, ни значение `version`. Разбор `pyproject.toml` как
  источник ожидаемой версии запрещён отдельно (`RK-02`);
- равенство вывода строковому литералу версии в любой форме;
- имена и сигнатуры внутренних функций; импорт внутренних функций в процессе
  теста на успешном пути (`CON-03` требует `subprocess`). Единственное
  исключение — `BEH-07`, где импорт в изолированном интерпретаторе и есть
  способ получить окружение без метаданных;
- дословный текст usage и дословный текст сообщения об отсутствии
  дистрибутива. Для `BEH-06` утверждается: stdout не содержит строки вида
  `smoke <версия>`, stderr непуст и содержит usage-признак. Для `BEH-07`:
  stdout не содержит версии, stderr непуст, в stderr нет признака traceback —
  это и есть проверяемая часть резолюции `Q-02`, тогда как формулировка
  сообщения остаётся свободной;
- содержимое stderr на успешном пути — behaviour-spec его не фиксирует
  (`BEH-01`);
- порог времени строже, чем 1 с: ужесточение превратило бы `NFR-01` в
  тест на производительность машины прогона;
- отсутствие сети через инспекцию состояния системы (`/proc`, вывод сетевых
  утилит, счётчики соединений) — утверждение делается через поведение под
  заглушкой;
- факты о git-истории, числе коммитов или их сообщениях.

**Карта red-проверок по сценариям** (адреса — из `checked_by` behaviour-spec,
подтверждённые резолюцией `Q-03`):

| Сценарий | Файл | Что красное до реализации |
|----------|------|---------------------------|
| BEH-01 | `tests/test_cli.py` | одна строка на stdout + код `0` |
| BEH-02 | `tests/test_cli.py` | равенство метаданным, вычисленным в прогоне |
| BEH-03 | `tests/test_cli.py` | разрешение имени команды из чужого `cwd` |
| BEH-04 | `tests/test_cli.py` | форма байтового буфера stdout |
| BEH-05 | `tests/test_cli.py` | pty-буфер == пайп-буфер |
| BEH-06 | `tests/test_cli.py` | usage на stderr + код `2`, версии на stdout нет |
| BEH-07 | `tests/test_cli_missing_distribution.py` | пустой от версии stdout + ненулевой код в изолированном интерпретаторе |
| BEH-08 | `tests/test_cli.py` | время < 1 с, неизменность FS с временным `HOME`, прогон под заглушкой сокета |
| BEH-09 | `tests/manual/version-bump-checklist.md` | ручная проверка, автотеста нет |

## Карта затрагиваемых модулей

Вход для стадии декомпозиции. Репозиторий пуст, поэтому все адреса —
создаваемые.

| Адрес | Статус | Назначение | Трассы |
|-------|--------|-----------|--------|
| `pyproject.toml` | new | `[project]` (name `smoke`, `version`, `requires-python >= 3.12`), `[project.scripts]`, `[build-system]`, dev-группа с `pytest`; рантайм-зависимостей нет | FR-02, NFR-03, CON-01, CON-02 |
| `src/smoke/__init__.py` | new | маркер пакета в src-раскладке; значения версии не содержит | CON-01, RK-02 |

## Вне объёма

Design сознательно оставляет реализатору:

- **код построчно.** Выше зафиксированы точки врезки, формы вызова и
  наблюдаемые свойства; тело `main()`, порядок операторов и способ
  форматирования строки — работа реализатора под TDD.
- **внутренние имена, кроме `main`.** Имена фикстур, вспомогательных функций
  и наличие `tests/conftest.py` как отдельного файла — на усмотрение
  реализатора, пока имена тест-функций совпадают с `target` из `checked_by`.
- **формулировки текстов.** Точная фраза сообщения об отсутствии
  дистрибутива, текст usage, язык и верстка `README.md` и ручного чеклиста.
- **выбор build-backend** в `[build-system]`: любой, при котором src-раскладка
  и `[project.scripts]` работают, а рантайм остаётся без сторонних
  зависимостей (`CON-02`).
- **число и границы коммитов** внутри пары red/green на сценарий: группировка
  близких сценариев в один red допускается, пока каждое падение остаётся
  содержательным.
- **значение версии при первой поставке** — это `Q-04`, owner_role: product;
  архитектурно безразлично, так как значение читается из метаданных.
- **стадия декомпозиции** получает карту модулей как вход и сама назначает
  порядок задач, исполнителей и формат приёмки по каждой задаче.
