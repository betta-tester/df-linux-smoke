# Decomposition — CLI-утилита `smoke`: команда `smoke --version`

Документ превращает утверждённые `20-design.md` (резолюции `Q-01`…`Q-06`,
карта модулей, рамки red-дизайна) и `25-acceptance.md` (критерии `AC-01`…
`AC-08`) в граф задач исполнения. Продуктовые и архитектурные решения здесь не
переоткрываются: нарезка проверок по файлам (`Q-03`), коды возврата (`Q-01`,
`Q-02`), механика изоляции сети (`Q-05`) и окружения без дистрибутива (`Q-06`)
приняты выше и входят в задачи как данность.

Сценарии `BEH-01`…`BEH-09` из `15-behaviour-spec.md` используются дословно;
новых сценариев и требований документ не вводит. Код не пишется: ниже только
границы задач, порядок и состав поставляемых результатов.

**Замечание о ссылках.** Узел декомпозиции не может править вышестоящие узлы,
поэтому там, где раздел «Механика» узла `design` не несёт собственного
стабильного идентификатора (таблицы точек врезки, форм инвокаций, форм
коммитов), `sources` ссылается на ближайший стабильный идентификатор, который
эту механику обязывает: резолюцию `design#Q-NN`, требование
`requirements#FR-…`/`NFR-…`/`CON-…` или сценарий `behaviour-spec#BEH-NN`.
Ни одна ссылка не указывает на номер строки или текст заголовка.

чтением вывода в байтах, без вложенного `uv run`.

`PackageNotFoundError` на границе `main()`, читаемое сообщение на stderr, код
возврата `1` — и единственный владеемый ею файл проверок
`tests/test_cli_missing_distribution.py`. Зависимость от DT-01 реальная, а не

коды `0`/`2` и файл `tests/test_cli.py` задача не трогает.

## Инварианты графа

- **Покрытие сценариев.** Девять сценариев разложены без пробелов и без
  пересечений: DT-01 → `BEH-01`, `BEH-02`, `BEH-03`, `BEH-04`, `BEH-05`,
  `BEH-06`, `BEH-08`; DT-02 → `BEH-07`; DT-03 → `BEH-09`. Каждый `BEH-NN`
  принадлежит ровно одной задаче.
- **Единственный владелец файла проверок.** `checked_by` сценариев дают три
  непересекающихся адреса: `tests/test_cli.py` (DT-01),
  `tests/test_cli_missing_distribution.py` (DT-02),
  `tests/manual/version-bump-checklist.md` (DT-03). Отсюда и число задач: три
  адреса проверок, утверждённые behaviour-spec и подтверждённые резолюцией
  `Q-03`, при правиле «один владелец на файл» и «один DT на сценарий» дают
  ровно три задачи. Дробить DT-01 дальше можно было бы только разнеся
  `BEH-01`…`BEH-06` и `BEH-08` по разным файлам — то есть переоткрыв `Q-03`,
  что этой стадии запрещено.
- **Ацикличность и отсутствие искусственной цепи.** Рёбер два: DT-02 → DT-01 и
  DT-03 → DT-01. Между DT-02 и DT-03 ребра нет, потому что реальной
  зависимости нет. Цикл отсутствует.
- **Топологический порядок объявления.** DT-01 объявлен до DT-02 и DT-03, то
  есть каждая задача объявлена после всех, от которых зависит.
- **Слияние групп.** Ни одна задача не зависит от участников двух и более
  групп: DT-02 и DT-03 имеют по одному ребру в единственную чужую группу
  `core`, сток которой — сам DT-01. Правило «зависеть от всех стоков каждой
  сливаемой группы» ни на кого не распространяется.
- **Уникальность DEL.** `DEL-01`…`DEL-17` объявлены по одному разу и не
  повторяются ни в одной другой задаче; каждый `statement` — одна строка.
- **`covered_by` только на свои сценарии.** `DEL-01` → `BEH-03`, `DEL-02` →
  `BEH-01`, `DEL-03` → `BEH-02`, `DEL-04` → `BEH-04`, `DEL-05` → `BEH-05`,
  `DEL-06` → `BEH-06`, `DEL-07` → `BEH-08` (все — сценарии DT-01); `DEL-13` →
  `BEH-07` (сценарий DT-02); `DEL-17` → `BEH-09` (сценарий DT-03). Остальные
  семь результатов — `DEL-08`…`DEL-12`, `DEL-14`, `DEL-15`, `DEL-16` — ни на
  один существующий пункт не ссылаются сознательно: их закрывают отдельные
  пункты чеклиста, потому что ни один сценарий behaviour-spec их не
  утверждает (единственность константы порога, текст README, структура
  модуля, единственность места с версией, содержательность первого red,
  читаемость сообщения на stderr, форма изолированного интерпретатора,
  самодостаточность ручного чек-листа).
- **Ни одного `delivered_by` и ни одного `verifies`.** Задач `type: verify` в
  графе нет, и это следствие предыдущих инвариантов, а не предпочтения: такая
  задача обязана нести непустой `scenarios`, а любой сценарий уже принадлежит
  владельцу своего файла проверок. Поэтому оба ключа отсутствуют во всех трёх
  задачах, как и требуется для `type: implement`.
- **Ни одного `tdd_waiver` и ни одного `negative_control`.** У DT-01
  зависимостей нет, значит честный red там и возможен, и обязателен. У DT-02
  честный red есть и описан в прозе (`DEL-14`). У DT-03 единственный
  `checked_by` — документ `kind: manual`, у него нет тест-узла, которым можно
  было бы назвать `negative_control`, поэтому класс `characterisation` к ней
  неприменим; ручная природа сценария зафиксирована самим behaviour-spec, а не
  оговоркой этой стадии.
- **Ни одного `restates`.** Повторяющихся обязательств в графе нет: `DEL-13`
  (отказ без дистрибутива) и `DEL-17` (видимость bump) не повторяют
  обязательств DT-01, а продолжают их — `DEL-03` утверждает равенство
  метаданным на установленном дистрибутиве, `DEL-17` — видимость смены
  значения после `uv sync`, и это разные обязательства, а не одно.

## Порядок и параллельность

| Группа | Задачи | Когда может идти |
|--------|--------|------------------|
| `core` | DT-01 | первой; зависимостей нет |
| `edges` | DT-02, DT-03 | после зелёного DT-01, одновременно друг с другом |

Группа `core` одиночна по составу: до появления установленной команды ни один
из остальных сценариев нечем наблюдать. Внутри DT-01 порядок — TDD-парами
red/green по сценарию или по связной группе сценариев; группировка близких
сценариев в один red допускается, пока каждое падение остаётся содержательным
(это оставлено design реализатору).

Задачи группы `edges` параллельны по-настоящему: они не делят ни одного файла
проверок, не делят продуктового кода (DT-03 продуктовый код не трогает
вообще) и обе читают результат DT-01 только как уже готовое поведение.
Единственная разделяемая поверхность — общая оснастка проверок: её автор
DT-01, DT-02 её расширяет, DT-03 не использует; поскольку оба ребра идут из
DT-01, одновременной правки оснастки двумя задачами не возникает.

Порог приёмки из `25-acceptance.md` закрывается так: зелёный DT-01 закрывает
`AC-01`, `AC-02`, `AC-03`, `AC-04`, `AC-06` и даёт три измеренные величины для
`AC-07`; DT-02 закрывает `AC-05`; DT-03 закрывает `AC-08`. Поставка
объявляется выполненной только после всех трёх задач — ни одна из них не
закрывает порог в одиночку.

## Вне объёма

Декомпозиция сознательно не дробит и не назначает:

- **Тело `main()` построчно, внутренние имена и формулировки текстов.** Design
  оставил это реализатору под TDD; задачи повторяют границу, а не сужают её.
- **Выбор build-backend, `.gitignore` и `uv.lock`.** Служебные артефакты
  окружения входят в DT-01 как часть работающей установки и отдельными
  задачами не заводятся: ни один сценарий их не наблюдает, а собственного
  результата, отличимого от `DEL-01`, они не дают.
- **Автоматизация `BEH-09`.** Решение `Q-03` — не автоматизировать на первой
  поставке; задачи на автоматизацию здесь нет и заводить её на этой стадии
  нельзя.
- **Значение версии при первой поставке.** `Q-04`, owner_role: product.
  Архитектурно безразлично, в задачи не входит, ни один `DEL` его не
  утверждает.
- **CI, публикация, релизный процесс, автоматический bump.** Вне объёма по
  `OUT-01` и `A-02`; задач под них нет.
- **Метрика M-01.** Измеряется ручной разметкой после поставки (`A-03`),
  критерием приёмки не является и задачей стать не может.
- **Дробление DT-01 на подзадачи по файлам продуктового кода.** `pyproject.toml`,
  `src/smoke/__init__.py` и `src/smoke/cli.py` не разводятся по отдельным
  задачам: сценарий `BEH-03` наблюдается только на всех трёх вместе, а задача
  без собственного сценария контрактом запрещена.
